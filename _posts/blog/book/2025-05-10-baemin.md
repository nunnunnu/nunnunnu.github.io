		2. develop 브랜치 -> ticket 브랜치 생성 -> 코딩

		4. 테스트 서버 배포
		5. 이상 없을 시 main 브랜치로 운영 서버 배포

### 4. 공동시스템개발팀의 코드 리뷰 문화 개선 이야기
- 기존 리뷰 과정
	1. MR 내용 작성
	2. 같은 파트원의 승인 후 머지
	3. MR, 리뷰 코멘트 발생 시 슬랙 알람
	- 그러나 리뷰가 늦어지는 문제&리뷰 작성에 많은 품이 소요됨으로 리뷰환경 개선
- 개선 과정
	1. MR 템플렛 사용
		- 기존에는 규칙이없었고 설명이 부족하였지만 템플릿을 만들어 해결
			- 해결하려는 문제가 무엇인가요?(ex. TS2305: Modul "react-router" has no exported member 'userHistory' 오류를 내면서 깨짐. 다른모듈에 의해 react-router 버전이 5->6으로 올라간것이 문제)
			- 어떻게 해결했나요?(ex. 사용하는 react-router 버전을 package.json에 명시)
			- MR의 Front 동작 이해를 돕는 GIF 파일 첨부
			- 리뷰어의 이해를 돕기 위한 모듈/클래스 설계 Diagram 포함
	2. 매일 아침 알람으로 MR목록 전송
		- 파이썬 깃랩을 이용해 파이썬 코드를 작성해 배치를 등록. 매일 지정시간에 알람이옴
	3. 칸반 리뷰 최대치 초과시 우선 리뷰하기로 규칙 지정
	4. 코드리뷰 규칙 문서 추가
		- 코드리뷰의 설명은 최대한 자세하게
			- 리뷰작성자는 본인이 알고있는 사항을 리뷰어들이 알거라는 가정을 버리고 충분한 문맥이 전달되게 리뷰설명 작성
			- MR템플릿에 맞춰서 작성
		- 작은 MR유지
			- 코드리뷰 크기는 삭제를 포함해 최대 300줄 미만으로 유지
			- 적합한 MR 단위
				- 하나의 티켓에 여러개의 MR 작성 가능
				- 리팩터링 작업 분리
		- 라벨로 코드리뷰의 우선순위 표기(D-n 규칙)
			- 코드리뷰가 완료되어야하는 시점을 D-n형식의 라벨로 코드리뷰에 추가.
			- 이슈가 없는 코드는 D-3, 당장 긴급한 리뷰는 D-0
			- 매일 라벨 업데이트
			- D-0이 된 다음날까지 리뷰가 달리지않았다면 코드베이스에 머지가능
		- 최소 한명의 리뷰를 받아야함
			- 같이 프로젝트를 진행하는 팀원의 리뷰를 받음
			- 필요하면 같이 프로젝트를 진행하지않는 팀원을 리뷰어로 할당해서 요청
		- 피드백을 반영하면 코멘트를 남김
		- 코드리뷰 코멘트에 강조하고싶은 정도 표기(Pn 규칙)
			- P1: 꼭 반영(Request changes)
			- P2: 적극적 고려(Request changes)
			- P3: 웬만하면 반영(comment)
			- P4: 반영해도좋고 넘어가도 좋음(Approve)
			- P5: 그냥 사소한 의견(Approve)
	5. 자동화로 쌓이는 리뷰 줄이기(파이썬 깃랩 이용)
		- 라벨 없을시 D-5, 하루씩 감소. D-0이되면 승인없이도 머지할수있게 규칙 추가

### 5. 팀문화의 탄생
- KRT(Keep, Problem, Try 의 준말로 회고 과정의 한 단계)를 진행. 남탓을 하면안되며 구체적이고 실천적이어야함.
- 반복되는 질문에 모두 답변. 질문하기를 꺼리는 분위기가 생기면 확인없이 배포했다가 장애가 발생할수도있음. 그럼에도 같은 질문이 계속된다면 업무 프로세스 문서화가 덜됐거나 의사소통의 명확성이 떨어지는것일수도있음. 왜 자꾸 같은 질문이 나오는지를 먼저 고민함
- 주석
	- 코드에 주석을 다는것을 죄악으로 보는 경우가있는데 '무엇을 하는지'에 관한 주석일때 그러함.
		- '무엇을 하는지'는 변수명이나 메서드 명으로 설명가능.
		- '왜 하는지'는 주석이 필요함. 상수의 이름이 이유를 알려주지않음
		- 코드와 최대한 가까운곳에 주석으로 이유, 문서링크를 달아주면 좋음
- 테스트
	- 젠킨스에서 빌드할때 코드 리버리지를 가장 최근 코드리버리지를 기록하고 그것보다 떨어지면 빌드를 실패하도록함
	- 젠킨스 JaCoCo플러그인과 그레이들 jaCoCo 조합으로 진행
	- 단, 코드리버리지에 지나치게 집착하면 assert문 없이 대충 코드를 순서대로만 실행하는 테스트 코드를 작성하는경우 발행 -> 올바르게 결과를 검증하지못하니 테스트코드가아님
- 정적분석
	- 소나큐브를 활용
	- Quality Gates라는 기능으로 정적분석 위반이 얼마간 발생할 경우 경고를 내보냄
	- SonarScanner for Jenkins Plugin: 젠킨스 파이프라인의 waitForQualityGate()가 젠킨스와 소나큐브의 상호작용을 가능하게함 -> 빌드자체를 Fail
- 페어프로그래밍
	- 항상 2명, 혹은 그 이상이 한대의 컴퓨터로 프로그래밍. 여러 논란이있지만 대부분 '장기적으로 유리하다'고 결론.

## 백엔드 개발자로 성장하기
### 1. 개발자 머피의 법칙
- 사용자의 입력은 무조건 검증
	- UI에서 하는 검증은 편리성을 위한 검증. 서버측에서도 검증되지않으면 클아이언트측에서 아무리 검증해도 검증되지않은것임.(가장 많이 일어나는 실수가 날짜임)
	- 모든 계산은 서버에서 할것. 
		- 프론트에서 상품 가격 등을 직접 받아서 결제를 한다면 앱개발을 조금만 아는 사람이라면 폼 값을 수정해서 서버에 요청을 날릴 수 있음.
		- <mark class="hltr-cyan">사용자의 입력 유효성 검사는 무조건 서버에서 해야하며, 계산로직은 사용자 편의를 위해 프론트에서 일시적으로 해서 보여줄 수는 있으나 최종 결과는 서버에서 재계산해야함</mark>
	- 사용자의 요청에 의해 쿼리의 모든 조건이 사라지면 안됨
		- where 1=1이 걸려있는 쿼리에서 아무런 조건도 입력하지않는다면 전체검색이 되니 무조건 검증해야함
		- 핵심은 where 1=1이 아는 '모든 조건이 사라진다'가 핵심. 
	- 동료 개발자의 요청도 믿어서는 안됨. 입력값은 무조건 검증할것.(페이지 사이즈를 1억으로 넣어 병목현상 발생)
- 성능 측정없는 캐시 사용은 성능을 저하시킬 수 있음
	- 멤케시드/레디스 같은 원격 분산 캐시는 네트워크 대역폭을 소모함. 캐시에 너무 많은 데이터를 담으면 캐시 히트율이 높더라고 네트워크 대역폭을 소모해 느려짐. AWS는 인스턴스 타입에따라 대역폭이 다르니 저장용량만으로 인스턴스 타입을 결정하면 안됨
	- 직렬화/역직렬화 시 성능테스트 필수
	- 또한 데이터 크기가 너무 크다면 압축 솔루션으로 전송량을 낮출 수 있음. 그러나 압축된 데이터를 풀고 직렬화 할때 CPU 점유율도 테스트해야함
	- 데이터 포맷 변경 시, <mark class="hltr-cyan">배포 전 캐싱한 데이터와 배포중인 서버에서 캐싱한 데이터가 서로 다른 필드를 가지게될수도있음. 둘중 한곳에서는 특정필드의 데이터를 누락시킨다는 것.</mark> DB칼럼처럼 전략을 세워 리팩터링 필요(로컬캐시 사용시 해당 문제가 해결되나 이 경우 데이터 동기화 문제를 해결해야함)
	- 캐시가 아니라 이미지 파일용량이 너무 큰경우에도 대역폭을 많이 소모해 성능이 저하될 수 있음. 이미지 크기를 최적화하고 CDN 사용 등으로 대역폭 문제가 발생하지않도록 해야함
- 인증/권한
	- 로그인한 회원이 요청한 자원의 권한을 가지고있는지 꼭 검증해야함
- 사용자의 로그인 실패 횟수를 트래킹해야함
	- 사용자의 로그인 횟수를 서버에서 관리하며, 일정 횟수 로그인 실패 시 이메일과 문자로 통보하는 방법 사용(비용문제 고려)
- 사용자의 가상재화는 별도 결제수단처럼 독립 인증해야함.
	- 다른 사이트에서 털린 정보로 우리 프로젝트에 인증해서 가상재화(포인트 등)을 사용할 수 있음. 이런 가상재화 사용 시 다른결제수단과 동일하게 별도인증 절차 필요
- 직원 PC에서 운영서버 API, DB 저장소 접근 통제
	- 운영 DB에 개발자가 붙어서 데이터를 잘못 수정할 수 있음.
	- <mark class="hltr-cyan">운영DB에 접근하는 계정(개발자, 애플리케이션 계정)은 통제된 몇명(DBA)이 아니면 가급적 DDL(가급적 DML까지) 권한 제거</mark>
	- MQ도 저장소니 동일하게 접근을 막아야함
	- 개발자는 운영 DB, API에 읽기 권한만 지급. 회사 직원이 사용하는 서비스는 회사망 내에서만 접근 가능해야함.
- 중요 배치는 실행여부를 제3의 시스템에서 검증해야함
	- 중요한 배치잡들은 별개의 모니터링 솔루션을 사용해 특정 시간 범위에 성공적으로 실행되었는지 확인, 실패한경우, 아예 작동하지않은 경우 모두 알람을 전송하도록 해야함. influxDB, 그라파나를 사용하면 가능
- 로그를 외부 서버로 수집하는 것은 별도 프로세스에서 비동기로.
- 기본키는 Integer가 아닌 Long으로
- 오류 로그는 일상적인 것과 크리티컬한 것을 분리.(회사정보가 공유가안되는것보다 공유했지만 중요도를 인지하지못하는 경우가 더 많음)
- 롤백 가능한 배포
- SPoF(Single Point Failure)를 제거.
	- 죽어도 괜찮은 서버를 구축해 단일 장애점을 제거. 내가 호출하는 애플리케이션이 죽는 경우도 염두에 두고 서킷브레이커 등을 도입하는것도 고려할 것.
- 이런일이 생길수도 있겠는데? 라는 생각이 드는 순간 <mark class="hltr-cyan">실제로 그 일이 발생했다고 가정해야한다.</mark> 판단결과 <mark class="hltr-cyan">장애의 정도가 크다면 그 장애는 이미 발생한것으로 간주.</mark> 그러나 감당가능한 수준이라면 넘어갈줄도 알아야함. 과한 대비는 서비스의 배포를 방해함

### 2. 메인 데이터베이스 IDC 탈출 성공기
- 과거 하나의 메인 데이터베이스로만 운영되었으나 메인 데이터베이스를 이관, 신/구 데이터베이스에 데이터 동시 적재 등의 과정을 거침
- 문제점
	- 프로시저 내부 로직은 모두 주석했지만, 프로시저는 남겨두어 호출하는부분 등 레거시는 아직 정리되지않은 상태
		- 그러나 신규 개발 후 새로 개발한 시스템이 아닌 레거시 시스템으로 연결되어 데이터 누수/병목 발생
	- 테이블 이름, 프로시저 명, 변수명 등 '이름'만으로는 목적을 알수없음.
	- 하나의 프로시저를 여러 시스템에서 호출을하고 여러 개발자가 수정하다보니 모두가 사용하지만 아무도 책임지지않는 경우 발생. -> 전체 로직 확인없이 필요부분만 조금씩 수정 -> 내가 수정한 부분 외 다른곳에서 어떤 문제를 야기하는지 파악 불가 -> 전체 시스템 불확실성 증가
	- 90프로는 같지만 10프로는 다른코드 발생.
- 배운점
	- 프로젝트를 계획할때 레거시 제거도 프로젝트 범위에 포함하자(일정 배분)
	- 명명 규칙을 미리 정하고 최대한 많은 사람에게 공유
	- 코드에 오너십을 갖기
	- 로직은 가급적 단순, 명로하게 구현

### 메세지 발송 이중화 여정기: 두개의 외부 시스템에 트래픽 분산

메세지 플랫폼에는 라우터(router)라는 모듈이 있는데 요청받은 메세지가 어떤 외부 시스템에 발송요청할지 결정, 요청을 넘겨주는 역할을 담당. 
라우터모듈에서 외부 시스템별 트래픽 비율정보를 알고있고, 비율에따라 A, B 외부 시스템으로 트래픽을 분산하도록 아키텍처를 결정.

- 요구사항
	- A 외부 시스템 장애상황에서는 B외부시스템으로만 요청이 가야함
	- B 외부 시스템 장애상황에서는 A외부시스템으로만 요청이 가야함
	- A 외부 시스템이 처리할 수 있는 동시 처리량을 넘어서는 때에는 B 외부 시스템에 트래픽을 50:50으로 분산
- 배포없이 트래픽 변경
	- 가중치 기반 라우팅 정책의 트래필 비율을 알고, 트래픽에따라 어떤 카프카 토픽으로 보낼지만 스프링 부트의 application.properties혹은 yaml 파일에 정하면 발송 이중화를구현가능
	- 하지만 시스템 운영중에도 배포없이 트래픽을 변경하려면 스프링 클라우드의 Config를 사용해 런타임에 프로퍼티 정보를 변경할 수 있는 기술도입이 가능함
		-  스프링 클라우드 Config + 스프링 클라우드 Bus + 스프링 클라우드 Config Monitor를 이용한 아키텍쳐
			1. DB의 프로퍼티 데이터 수정 -> Config 서버 애플리케이션에서 스프링 클라우드 Config Monitor에서 제공하는 /monitor 엔드포인트 호출
			2. /monitor 엔드포인트로 요청된 정보를 바탕으로 카프카에 클라이언트의 프로퍼티 정보를 갱신하도록 하는 RefreshRemoteApplicationEvent를 발행
			3. 클라이언트는 카프카 토픽을 구독하고 있고 이벤트를 수신해 클라이언트의 프로퍼티 정보를 갱신
			4. 클라이언트를 갱신 시, Config 서버에 자신의 application-name과 profile정보를 기반으로 프로퍼티 정보 조회
			5. Config 서버는 요청받은 application-name과 profile 정보를 기반으로 DB에 저장된 프로퍼티 정보를 조회해 API응답으로 반환
			6. 조회된 프로퍼티 정보를 기반으로 클라이언트에 @RefreshScope로 등록된 bean을 재생성
			- 장점: 프로퍼티 수정 발생시 Config의 /monitor 엔드포인트를 호출해 클라이언트별로 1회만 API를 호출, 변경사항 반영. 실시간에 가까움
			- 단점: 클라이언트에 이벤트를 전파하기위해 메세지브로커(카프카 등)이 필요. 메세지 브로커가 정상적이지않다면 설정변경 불가능
		- 스프링 클라우드 Config + Scheduled Polling을 이용한 아키텍쳐 <- 선택
			1. 메세지 플랫폼 라우터 모듈에서 10초 주기로 Config 서버에 application-name과 profile 정보를 기반으로 DB에 저장된 프로퍼티 정보를 조회해 API 응답으로 반환
			2. config서버는 요청받은 appliation-name과 profile 정보를 기반으로 DB에 저장된 정보를 조회해 API값으로 반환
			3. state라는 필드를 사용해 state값이 변경된 때에만 ContextRefresh를 하도록함. state값이 변경되지않은 때에는 Context Refresh를 실행하지않도록해 비효율적으로 Bean을 재생성하는 과정 제거. state값에 가장 최근에 변경된 프로퍼티 수정시간 timestamp값을 사용
			4. 응답정보의 state값이 변경된 때에는 조회된 프로퍼티정보를 기반으로 클라이언트에 @RefreshScope로 등록된 Bean을 재생성
			- 장점: 메세지 브로커 관리비용 없음
			- 단점: 클라이언트가 주기적으로 Config서버에 프로퍼티 조회 API를 요청하는 구조. 클라이언트 개수가 늘어나면 Config서버로의 조회요청이 선형적으로 증가 -> 클라이언트 개수 증가시 트래픽 증가

### 배민상회와 검색 플랫폼 연동기
- 기존 - 엘라스틱서치에 like 검색을 함
	- 문제
		- 적절한 동의어나 유사어 사전구축의 어려움
		- 찾고싶은 항목 검색보다 정확한 검색에 초점을 맞추고있음
		- 인프라 유지 부담: 노드를 유지하기위한 인스턴스 구성, 모니터링, 색인 관리 등 엘라스틱서치를 유지하기위한 개발 리소스 필요
	- 구조
		![image](/assets/images/book/IMG-20250720135902-1.png)
- 검색 시나리오
	- 단순 키워드 검색 뿐만 아니라 카테고리에 속하는 목록을 가져와야함
	- 키워드 검색 - 문자열 검색, 카테고리검색 - 숫자 검색
		=> 검색어 형태가 다르게때문에 이를 포괄하여 추상화 할 수 있는 개별 객체 필요.
	- 검색 종류를 추상화하는 인터페이스 + 이를 구현하는 개별 비지니스 로직 별 검색종류 enum
- 신규
	- 구조
		![image](/assets/images/book/IMG-20250720135902-2.png)
	- 자체 DSL()
		- DSL: 쿼리를 사용하는 분야에서 해당분야에 적합하도록 만든 자체적인 질의 언어
		- 검색플랫폼의 QueryDSL: QueryDSL에 검색어와 관련된 쿼리부분을 제외하고 판매 기간이나 판매 상태들을 조건에 추가
		- 엘라스틱서치의 QueryDSL: 검색어와 관련된 부분도 쿼리로 만들어야하며 판매기간, 상태 등의 조건도 개별 boolean문으로 만들어줘야함

## 발단

이전 회사에서 운영하던 서비스는 주문이 들어오면 OpenAI로 리포트 내용을 생성하고, 그 결과로 PDF를 만들어 고객에게 메일로 보내주는 구조였다.

- 대량으로 들어오는 일반 주문은 <mark class="hltr-cyan">OpenAI Batch API</mark>로 처리
	- 요청을 JSONL 파일로 만들어 업로드 -> 배치 생성 -> 상태 확인 -> 결과 파일 다운로드
- 바로 받아봐야하는 실시간 주문은 Chat API를 바로 호출

각 단계는 스케줄러가 상태값을 보고 다음 단계로 넘기는 방식이었고, 배치 자체가 실패했을때 다시 시도하는 로직은 이미 들어가 있었다.

그런데 어느날 OpenAI 쪽 서버 에러로 <mark class="hltr-cyan">배치 결과 파일 다운로드가 실패</mark>했다.
배치는 끝났는데 결과를 못가져온 상태라 해당 주문들은 처리중으로 남았고, 고객에게 리포트가 나가지 않았다.

기존 재시도 로직은 배치가 실패한 경우만 다루고 있어서, 이렇게 중간에 멈춘건은 아무도 다시 집어가지 않는 상황이었다.

## 재시도 스케줄러 추가

그래서 중간에 멈춘 건을 주기적으로 다시 요청하는 재시도 스케줄러를 추가했다.

먼저 재시도 대상을 정했다.

- 생성된지 <mark class="hltr-cyan">2시간이 지났는데도</mark> 실패/처리중/재시도 상태로 남아있는 프롬프트
	- 정상적으로 처리되고 있는 건까지 다시 요청하면 같은 리포트가 두번 생성되기 때문에, 충분히 시간이 지난 건만 대상으로 잡았다

실행 주기는 주문 유형별로 나눴다.

```java
// 예시 코드
@Scheduled(cron = "0 0 */4 * * *")
public void retryNormalOrders() {
    LocalDateTime limit = LocalDateTime.now().minusHours(2);
    List<PromptProcess> targets = repository.findStuckProcesses(
            List.of(FAIL, PROCESSING, RETRY), limit);

    for (PromptProcess process : targets) {
        eventPublisher.publishEvent(new PromptRetryEvent(process.getId()));
    }
}
```

그리고 일반 주문의 발송 시간도 10시, 18시로 옮겼다.
새벽에 실패가 나면 아침에 출근해서야 알게되는데, 업무 시간 안에 발송되면 실패가 나도 바로 대응할 수 있기 때문이다.

>[!재시도 기준은 한번 더 바뀌었다]
>
>처음에는 프롬프트 한건 한건의 상태를 보고 재시도 대상을 골랐는데, 일반 주문은 배치 단위로 묶여서 처리되기 때문에 OpenAI 배치 단위로 실패를 판단하도록 바꿨다.
>실시간 주문은 한건씩 처리되니 그대로 두었다.
>

## OpenAI가 결과를 빼먹은 경우

한달쯤 뒤에는 다른 형태의 문제가 생겼다.
배치는 정상 완료로 끝났는데 <mark class="hltr-cyan">결과 파일 안에 일부 요청의 결과가 아예 없었다.</mark>

상태가 실패도 아니고 결과도 없으니 이것도 처리중으로 남아버렸다.
일단 해당 건들은 수동으로 재시도해서 발송을 마쳤고, 이런 경우에도 강제로 재시도할 수 있는 기능을 추가했다.

외부 API가 "완료"라고 해도 내가 보낸 요청 수와 받은 결과 수가 맞는지는 따로 확인해야한다는걸 이때 알았다.

## 1698년생 한명 때문에 배치 전체가 안만들어진 이야기

연말에는 더 황당한 일이 있었다.
생년월일이 1698년으로 들어온 주문이 하나 있었는데, 사주 계산에 쓰는 절입 시각 데이터에 그 연도가 없어서 에러가 났다.

문제는 이 에러가 그 주문 하나로 끝나지 않았다는 것이다.
배치용 JSONL 파일을 만드는 반복문 안에서 예외가 터지면서 <mark class="hltr-cyan">그날 일반 주문 전체의 배치가 생성되지 않았다.</mark> (한명 때문에 전원 대기..)

그래서 세가지를 고쳤다.

1. 한건이 실패해도 나머지는 배치에 들어가도록 반복문 안에서 예외를 잡고, 실패한 건은 따로 실패 처리
	```java
	// 예시 코드 (실제 코드와 다름)
	for (PromptProcess process : targets) {
	    try {
	        writer.write(toJsonLine(process));
	        writer.newLine();
	    } catch (Exception e) {
	        log.error("배치 생성 제외 processId={}", process.getId(), e);
	        process.fail(e.getMessage());
	    }
	}
	```
2. 어떤 주문이 왜 실패했는지 바로 알수있게 에러 로그 강화
3. 주문 생성 단계에서 1900년 미만 생년월일은 유효성 검사로 막기

3번만 했어도 이번 건은 막을 수 있었겠지만, 다음에 또 다른 이상한 데이터가 들어올수도 있으니 1번이 더 중요하다고 생각햇다.

## 정리

외부 API에 의존하는 파이프라인을 운영하면서 정리한 것들

- 외부 API는 언젠가 실패한다고 가정하고, <mark class="hltr-cyan">상태값을 보고 멈춘 건을 다시 집어오는 스케줄러</mark>가 있어야한다
- "완료" 응답을 그대로 믿지말고 보낸 요청과 받은 결과가 맞는지 확인한다
- 한건의 실패가 전체를 막지 않도록 실패를 격리한다
- 입력 단계에서 막을 수 있는 데이터는 미리 막는다
- 장애가 나도 사람이 대응할 수 있는 시간에 돌도록 발송 시간을 조정한다

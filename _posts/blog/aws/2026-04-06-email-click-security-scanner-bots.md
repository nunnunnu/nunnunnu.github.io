## 발단

메일을 보내고 링크별 클릭을 집계해봤는데 숫자가 좀 이상했다
본문 버튼보다 푸터에 있는 <mark class="hltr-cyan">이용약관/개인정보 처리방침/고객지원 링크</mark> 클릭이 생각보다 많았고 이용약관과 개인정보 처리방침의 고유 클릭자 수는 딱 같았다

푸터 링크를 그렇게 열심히 누르는 사람은 잘 없고 사람이 누른거라면 두 숫자가 이렇게 깔끔하게 맞을리도 없는데..

---

## 클릭 추적은 "누가 눌렀는지"를 모른다

일단 클릭 추적이 어떻게 동작하는지부터 다시 찾아봤다

SES에서 클릭 추적을 켜면 발송할때 본문의 링크를 전부 추적용 리다이렉트 주소로 바꿔서 보낸다
수신자가 링크를 누르면 요청이 먼저 SES의 추적 주소로 가고 SES는 Click 이벤트를 기록한 다음 원래 주소로 리다이렉트 시킨다
우리는 이 이벤트를 SNS로 받아서 쌓는 구조였다

여기서 SES가 기록하는건 <mark class="hltr-cyan">"이 추적 주소에 HTTP 요청이 왔다"</mark>가 전부이다
요청한 쪽이 사람이 쓰는 브라우저인지 프로그램인지는 구분하지 않고 Click 이벤트에 같이 실려오는건 클릭한 링크/시각/User-Agent/IP 정도다

오픈 추적도 원리가 같다. 본문에 1x1 이미지를 심어두고 그 이미지가 요청되면 오픈으로 센다
그래서 메일 클라이언트가 이미지를 미리 받아두면 사람이 안 열어도 오픈이 찍힌다

---

## 보안 스캐너는 왜 링크를 누르나

기업 메일은 앞단에 보안 게이트웨이를 두는 경우가 많은데
이런 제품 중에는 메일이 도착하면 본문 링크를 <mark class="hltr-cyan">직접 열어보고 피싱이나 악성 페이지인지 검사</mark>하는 것들이 있다고 한다
방식은 제품마다 다르지만 사람이 누르기 전에 기계가 먼저 링크를 방문한다는 점은 같다

이 방문이 클릭 추적 입장에서는 그냥 클릭이다. 대신 기계가 하는 일이라 흔적이 사람이랑 다르다

- 사람이 고르는게 아니니 링크를 전부 연다(푸터 링크도 예외없이)
- 한꺼번에 여니까 링크 사이 간격이 ms 단위
- 검사용 브라우저가 오래된 경우가 있어서 User-Agent가 이상함
- 검사 엔진이 여러개면 같은 링크 묶음을 여러번 훑음

## 로그를 수신자 단위로 펼쳐보기

링크별 합계만 봐서는 이게 안 보여서 클릭 이벤트를 <mark class="hltr-cyan">수신자 단위로 묶고 시간순으로</mark> 펼쳐봤더니 바로 보였다

- 메일 안의 링크 전체를 0~1.5초 안에 클릭
- 어떤 수신자는 링크 6개를 17ms 안에 전부 클릭
- 여러 링크의 클릭 간격이 0.0초(사실상 동시)
- User-Agent가 IE11(Trident/7.0). 지금 IE11로 메일 링크를 누르는 사람은 없다고 봐도 된다
- User-Agent 두개가 33초 간격으로 같은 링크 묶음을 두번 훑고 지나감

위에서 찾아본 스캐너 특징이랑 그대로 맞았다. 사람은 링크 6개를 17ms 안에 누를 수 없다;;

## 판정 기준 만들기

### 1차: 푸터 링크를 전부 누른 수신자

처음엔 단순하게 "푸터 링크 3종을 모두 누른 수신자"를 의심 대상으로 잡고 걸린 수신자를 클릭 간격과 User-Agent로 하나씩 확인했다
수동으로 훑어보는 용도로는 괜찮았는데 기준으로 굳히기엔 약했다. 메일마다 푸터 구성이 다를수도 있고 사람이 정말 약관을 누를수도 있기때문

### 다시 뽑은 기준: 속도

스캐너와 사람의 차이를 속도로 보면 메일 구성과 상관없는 기준이 된다
사람은 링크 하나를 누르면 새 탭이 열리고 페이지를 보기때문에 다음 링크를 누르기까지 최소 몇 초는 걸린다
그래서 <mark class="hltr-cyan">아주 짧은 시간 안에 서로 다른 링크를 여러개</mark> 누른 기록이면 사람으로 보기 어렵다고 판단했다

```typescript
// 예시 코드
const MIN_DISTINCT_LINKS = 3;
const MAX_SPAN_MS = 2_000;

interface ClickRow {
  recipientId: string;
  link: string;
  userAgent: string | null;
  clickedAt: number; // epoch ms
}

function findScannerRecipients(rows: ClickRow[]): Set<string> {
  const byRecipient = new Map<string, { links: Set<string>; times: number[] }>();

  for (const row of rows) {
    if (isBotUserAgent(row.userAgent)) continue; // UA로 이미 걸린 클릭은 여기서 빼고 따로 처리
    const r = byRecipient.get(row.recipientId) ?? { links: new Set<string>(), times: [] };
    r.links.add(row.link);
    r.times.push(row.clickedAt);
    byRecipient.set(row.recipientId, r);
  }

  const scanners = new Set<string>();
  for (const [id, { links, times }] of byRecipient) {
    const span = Math.max(...times) - Math.min(...times);
    if (links.size >= MIN_DISTINCT_LINKS && span <= MAX_SPAN_MS) scanners.add(id);
  }
  return scanners;
}
```

User-Agent 기준은 따로 두었다
오래된 브라우저 시그니처나 UA 문자열에 보안 제품이나 메일 프록시 이름이 그대로 들어오는 경우가 있어서 키워드 목록으로 거른다

그럼 UA로 걸린 클릭은 왜 시간 기준 판정에서 뺐을까?
추적 링크는 수신자별로 발급되니까 스캐너가 누른 클릭도 그 수신자의 클릭으로 찍힌다
이미 봇으로 확인된 클릭까지 섞어서 세면 사람이 누른 클릭 근처에 찍힌 스캐너 클릭때문에 사람까지 스캐너로 묶일 수 있어서 빼주었다

## 봇이랑 사람이 섞여 있는 경우

애매한 케이스가 하나 있었다

한 수신자는 처음에 0.06초 만에 링크들을 훑은 기록이 있고 그 뒤로 6초~90초 간격으로 링크를 하나씩 누른 기록이 이어졌다
앞부분은 스캐너고 뒷부분은 메일을 받은 사람이 직접 열어서 누른 것이다(같은 메일함을 스캐너도 열고 사람도 연다)

이 수신자를 통째로 봇으로 빼면 실제 클릭자를 하나 잃는다
위 기준은 수신자의 전체 클릭 시간 폭을 보니까 사람이 나중에 누른 기록이 있으면 폭이 2초를 넘어서 봇으로 안 잡힌다
고유 클릭자 수를 셀때는 이걸로 원하는 결과가 나왔다

다만 누적 클릭 수까지 정확히 하려면 얘기가 다르다. 이 수신자의 클릭에는 스캐너가 만든 클릭이 그대로 섞여있기때문
결국 정확한 단위는 "이 수신자는 봇이다"가 아니라 <mark class="hltr-cyan">"이 클릭 묶음은 봇이 만든 것이다"</mark>였다
누적 수치까지 걸러야 하면 수신자별 클릭을 시간 간격으로 묶음(burst) 단위로 잘라서 묶음마다 판정해야한다

## 집계할때 챙긴 것

**판정은 집계 대상 링크로 좁히기 전에**

캠페인 성과는 본문 버튼 같은 몇개 링크만 보면 되니까 그 링크로 먼저 거르고 싶어진다
그런데 스캐너는 푸터까지 다 훑기때문에 대상 링크만 남긴 다음 판정하면 스캐너도 "링크 1개 클릭"으로 보여서 기준에 안 걸린다
그래서 판정은 전체 클릭으로 하고 집계를 좁히는건 그 다음에 했다

**원본 수치와 봇 제외 수치를 둘다 남긴다**

SQL에서 처음부터 봇을 걸러버리면 "얼마나 걸러졌는지"를 비교할 기준이 사라져서 지표를 나눠서 정의했다

| 지표 | 정의 |
|---|---|
| 클릭수 | 1회 이상 클릭한 고유 수신자 수 |
| 순클릭수 | 봇 의심 클릭과 푸터 링크 클릭을 뺀 고유 수신자 수 |
| 누적 클릭수 | 같은 수신자의 중복 클릭까지 포함한 총 횟수 |

**수신거부 링크도 스캐너가 누른다**

봇을 빼고 다시 집계하니 본문 버튼 클릭자도 수신거부 링크 클릭자도 눈에 띄게 줄었다
수신거부 링크도 스캐너가 같이 누르니까 걸러내기 전에는 수신거부 반응이 실제보다 훨씬 나빠 보였던 것이다

---

클릭 수가 이상할때는 링크별 합계말고 수신자 단위로 시간순으로 펼쳐보는게 제일 빨랐다
누적 클릭수까지 맞추려면 수신자가 아니라 묶음 단위로 판정해야한다는것도 알게됐다
